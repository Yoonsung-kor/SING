# AI 활용 계획

처음 작성: 2026-10-13, 갱신: 2026-11-18. **곡 추천, 곡 최고음 찾기, 연습 피드백(허밍·따라 부르기)에는 OpenAI 호출이 연결되어 있다. 맞춤 연습과 주간 변화 요약은 아직 계획이다.** 구현된 기능의 실제 동작은 [README](../README.md)와 [시스템 구조](architecture.md)에 있다.

## 측정과 설명의 역할

프로젝트에서 확인하려는 것은 ‘목표 음정이 맞는지’와 ‘음을 유지하는 동안 음높이가 얼마나 변하는지’다. 이를 발표에서는 **음정 정확도·음높이 유지 안정성 분석**으로 표현한다. 악센트나 음색 측정은 현재 범위와 다르다.

현재 `pitch.js`가 단일 음의 주기성을 분석해 주파수와 음이름을 추정한다. 음높이 변화 관련 임계값은 신뢰도 판정에 사용하지만, 사용자가 볼 수 있는 시간별 변화 그래프나 별도의 안정성 점수는 아직 제공하지 않는다.

먼저 앱이 수치를 계산하고 실제 기기에서 검증한다. 생성형 AI는 이 수치와 체감을 근거로 결과를 설명하고 다음 과제를 제안하는 역할을 맡길 계획이다.

## 기능별 입력 → 처리 → 출력

| 기능 | 입력 | 처리와 AI의 역할 | 출력 | 선행 조건 |
| --- | --- | --- | --- | --- |
| 연습 피드백 | 목표음, 유효 구간의 음높이 변화, 목표와의 차이, 유지 시간, 측정 신뢰도, 체감 | 분석 코드가 수치를 계산하고 생성형 AI가 관찰 내용을 설명 | 이번 시도 요약, 확인할 점, 다음 행동 | **구현(2026-11):** 허밍 결과와 노래 따라 부르기에 연결. 따라 부르기는 2026-11-18부터 "어려운 자리" 리포트다. 자리·결과·연습은 코드가 정하고 리포트는 AI 없이도 나온다. AI는 자리마다 문장만 다듬고, 빠진 자리와 근거 없는 문장은 코드의 문장으로 바뀐다. 남은 일은 이어폰으로 부른 실제 녹음으로 기준값을 다시 맞추는 것이다. 노래방 녹음 리포트(2026-11-18)도 같은 문장 다듬기를 쓴다. 녹음 분석은 폰 안의 코드가 하고 AI는 녹음을 듣지 않는다. |
| 맞춤 연습 | 최근 결과, 목표, 가능한 시간, 준비된 연습 목록 | 조건에 맞는 과제를 제한한 뒤 AI가 선택 이유 설명 | 추천 과제와 시간, 선택 이유 | 연습 콘텐츠와 진행/중단 규칙 검토 |
| 곡 추천 | 출처가 확인된 곡 음역·원키, 개인 키, 취향, 실제 곡 체감 | 코드가 비교 가능한 후보를 찾고 AI가 추천 이유 설명 | 후보 곡, 비교 근거, 부족한 정보 | **1차 구현(2026-11):** 플레이리스트 이름과 담긴 곡을 근거로 AI가 웹 검색으로 실제 곡을 확인해 후보와 이유를 내고, 서버가 출처·음 표기·중복을 검증한다. 키 제안은 코드가 계산한다. |
| 주간 변화 요약 | 같은 과제의 누적 지표와 체감 | 비교 가능한 기록을 묶고 AI가 변화를 설명 | 이번 주 변화와 다음 목표 | 반복 기록과 비교 기준 |

## 첫 AI 기능의 범위

1. 짧은 한 음 연습을 대상으로 목표음과의 차이, 음높이 변화, 유효 음성 길이와 신뢰도를 정의한다.
2. 낮은 신뢰도와 누락값을 성공이나 0점으로 처리하지 않는다. 사용자 체감은 별도 필드로 유지한다.
3. 이 구조화된 결과만으로 짧은 피드백을 생성하는 기능부터 연결한다.
4. 다음 과제는 검토된 콘텐츠 목록 안에서 선택하게 한다.
5. API 실패·응답 오류 시에는 측정 사실에 기반한 기본 안내를 제공한다.

음높이가 흔들렸다는 사실만으로 호흡·성대·발성 습관의 원인을 단정하지 않는다. 점수·수치·존재하지 않는 곡 정보를 모델이 만들어내지 않도록 응답을 검증한다.

## 데이터와 시스템 설계 예정

- API 키는 추가할 서버에서 관리한다. 브라우저 코드에 넣지 않는다.
- 초기 연결은 원음보다 측정 지표와 필요한 이력을 중심으로 설계한다.
- 외부 전송 항목과 사용 목적은 연결 전에 화면에서 안내하고 동의 흐름을 준비한다.
- 모델과 제공자는 응답 품질·지연·비용·데이터 처리 조건을 비교한 후 정한다.
- 학습 기반 음높이 추정 모델은 현재 알고리즘과 실제 녹음으로 비교할 필요가 생겼을 때 검토한다.

## 검증 기준

| 확인할 질문 | 검증 방법 |
| --- | --- |
| 측정값이 실제 입력을 반영하는가? | 알려진 기준음, 녹음, 소음·무음·불안정 입력을 비교하고 기기 정보를 기록 |
| 설명이 입력과 일치하는가? | 정답 음정·목표 불일치·신뢰도 부족·체감 불편 사례를 고정해 설명 검토 |
| 연습이 적절한 목록에서 선택되는가? | 과제 ID와 진행 조건 검증, 중단 조건에서 발성 과제를 제안하는지 확인 |
| 없는 곡 정보를 만들지 않는가? | 후보 ID·출처·입력 음역과 응답 비교, 정보 부족 시 미확인 처리 |
| 서비스 연결이 실패해도 연습을 이어갈 수 있는가? | 시간 초과·응답 오류 시 기본 피드백과 기록 보존 확인 |

수치 임계값과 모델 성능 목표는 실기기 기준 데이터를 모은 뒤 정한다. 현재의 자동 테스트 통과는 보컬 개선 효과를 검증한 결과가 아니다.

## 확인 기록

**2026-11-18 · 노래방 녹음 리포트 (AI 없이 폰에서 분석)**

- 왜: 11/6에 녹음을 직접 듣는 AI는 시간과 가사를 지어냈다. 그래서 녹음은 AI에 보내지 않고, 반주 속에서 목소리의 음을 따라가는 분석기를 브라우저 코드로 만들었다.
- 근거: 실험([결과 문서](superpowers/specs/2026-11-16-karaoke-experiment-results.md)의 표)에서 이 분석기가 실제 노래방 녹음 4곡의 목소리 구간 87%·98%·89%·94%를 반음 이내로 맞혔다(앱의 기존 탐지기 27%). 섞인 소리에서 믿을 만한 자리는 길게 낸 높은 음뿐이었다(떼어 낸 목소리와 약 80% 일치). 큰 도약과 짧은 높은 음은 틀릴 때가 많았다.
- 그래서: 노래방 리포트는 길게 낸 높은 음과 그 음을 지켰는지만 말하고, 짧은 음·도약·끊김은 말하지 않는다. 편한 최고음은 길게 지킨 음이 두 번 이상, 지금 값보다 4반음 안쪽으로 높을 때만 바꿀지 묻는다. 자동으로 바꾸지 않는다.
- AI가 하는 일: 따라 부르기와 같다. 자리의 종류·결과·음 이름만 받아 문장을 다듬고, 서버와 앱이 검사한다. 녹음, 시간, 가사는 보내지 않는다.
- 한계: 녹음 4개, 가수 한 명, 정답은 분리 모델이 떼어 낸 목소리에서 잰 음이다(사람이 들은 정답이 아니다). 분석기의 값은 그 시험 소리를 보며 골랐다. 짚은 자리가 맞는지는 노래방에서 사용자가 귀로 확인한다(목표: 10곳 중 8곳).

**2026-11-18 · 따라 부르기 리포트를 "어려운 자리"로 바꿈**

- 왜: 줄마다 끊김·흔들림·높음 비율을 재던 피드백은 평범하게 부른 줄도 문제로 잡았다(멜로디가 움직이면 흔들림, 자음과 숨은 끊김). 11/16에는 코드가 찾은 문제 2개 중 AI가 1개만 말했다. 실제 목소리 4곡으로 미리 돌려 보니 끝으로 갈수록 처진 음은 곡당 0~1개였다.
- 이제: 코드가 노래에서 힘든 자리(큰 도약, 길게 낸 높은 음, 편한 최고음보다 높은 음)와 결과(지켰다, 내려왔다, 끊김은 묻기)를 많아야 3곳 고른다. 연습은 출처를 확인한 알아두기 칼럼을 줄인 목록에서 코드가 고른다.
- AI 없이도 나온다: 자리마다 코드의 문장이 있어서 동의가 없거나 AI가 실패해도 리포트가 바로 뜬다.
- 빠진 자리는 코드가 채운다: AI가 빠뜨린 자리, 받지 않은 음 이름·시간·숫자·따옴표가 있는 문장, 끊김을 단정한 문장은 코드의 문장으로 바뀐다. 서버와 앱이 두 번 검사한다.
- 확인: 실제 OpenAI 문장 9개 중 9개 통과(바뀐 것 0). 일부러 모든 문장에 시간을 넣은 가짜 답은 9개 모두 코드의 문장으로 바뀌었다(자동 테스트). Chrome에서 심은 세 자리를 그대로 짚었다.
- 한계: 기준값은 노래방 녹음에서 떼어 낸 목소리로만 대강 맞췄다. 떼어 낸 목소리 4곡에서 고른 12곳 중 4곳이 "확인해 볼 자리"(끊김)였다. 같은 음의 두 글자 사이 자음일 수 있어 실제 녹음으로 다시 본다.
